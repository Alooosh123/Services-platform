## إدارة التطبيقات والهوامش حسب الباقة وقنوات الدفع الديناميكية
**الإصدار:** v1.0 | **التاريخ:** 11 أكتوبر 2026 | **المرحلة:** P06

### 1. جدول مقارنة البنية البرمجية (Existing vs Missing vs Conflict vs Risk)

| العنصر | الحالة في الكود الحالي (Existing) | النواقص المطلوبة في P06 (Missing) | التعارضات المحتملة (Conflict) | المخاطر والضوابط (Risk & Controls) |
|:---|:---|:---|:---|:---|
| **1. طلبات إضافة التطبيقات (`ServiceRequest`)** | لا يوجد نموذج لاستقبال طلبات التطبيقات؛ الكتالوج ثابت في الذاكرة ومقيد بـ Seed محدد. | نموذج `ServiceRequest` بقاعدة البيانات، واجهة للعميل لطلب تطبيق أو باقة (`POST /api/catalog/service-requests`)، وطابور للمدير (`GET/PATCH /api/catalog/admin/service-requests`). | لا يوجد تعارض مباشر. | خطر تراكم طلبات غير واقعية؛ الضابط: تقييم إداري وحالات (`PENDING`, `APPROVED`, `REJECTED`, `FULFILLED`). |
| **2. إدارة الكتالوج الديناميكي (Dynamic CRUD)** | عمليات قراءة فقط واستعلام بالـ slug، مع دالة `createService` أولية بدون واجهات تعديل/حذف للفئات والباقات والحقول. | واجهات CRUD متكاملة للصنف (`ServiceCategory`), الخدمة (`Service`), الباقة (`Product`), والحقول (`ServiceField`)، مع دعم الصور، الترتيب (`displayOrder`), والتعطيل الفوري. | لا يوجد تعارض. | خطر حذف منتج له طلبات تاريخية؛ الضابط: Soft Delete (`isActive = false`) ومنع الحذف الصلب للباقات المرتبطة بطلبات. |
| **3. اشتراط ربط المزود قبل النشر (Provider Mapping Gate)** | يمكن إضافة منتج دون تحديد مزود أو آلية تنفيذ. | حظر نشر أي خدمة أو باقة (`isActive = true`) دون تعيين مزود شحن رسمي (`providerId` أو `providerProductSku`) أو تفعيل وضع التنفيذ اليدوي (`isManualFulfillment = true`). | لا يوجد تعارض. | خطر بيع منتج لا يمكن تنفيذه للعميل؛ الضابط: Gating صارم يمنع النشر دون مسار تنفيذ مؤكد. |
| **4. محرك التسعير والهوامش الهرمية (`PricingEngine`)** | أسعار ثابتة مخزنة في `product_prices` لكل عملة بدون محرك قواعد وهوامش ديناميكية. | محرك تسعير متقدم يدعم هرمية القواعد: `DEFAULT` ↔ `CATEGORY` ↔ `SERVICE` ↔ `PRODUCT`، هوامش ثابتة أو نسبية (`FIXED`, `PERCENTAGE`)، مع نطاق زمني للصلاحية (`validFrom`, `validTo`). | لا يوجد تعارض مع الطلبات السابقة طالما تحافظ على `OrderSnapshot`. | خطر تسعير ينتج عنه بيع بخسارة؛ الضابط: معادلة `Retail = Cost + Validated Fees + Policy Margin` مع حد أدنى للهامش (`minMargin`). |
| **5. إصدارات قواعد التسعير وحماية تاريخ الطلبات (Pricing Versioning)** | لا توجد إصدارات لقواعد التسعير. | نموذج `PriceRuleVersion` مع توقيع المعدل (`createdByUserId`) وسبب التعديل (`changeReason`)، مع إثبات أن تعديل الأسعار لا يعيد تسعير تاريخ الطلبات السابقة (AT-12, AT-22). | تضارب محتمل إذا حاولت وحدة إعادة احتساب أرباح طلبات قديمة. | الضابط الصارم: `OrderSnapshot` مجمد وغير قابل للتعديل (Immutable). |
| **6. إدارة قنوات الدفع والمراجعة المالية المزدوجة (Dual Control / Four-Eyes)** | قنوات الدفع تدار عبر محولات ثابتة و`PaymentChannelConfig` أولي. | واجهة إضافة وتعديل قنوات الدفع ديناميكياً مع اشتراط موافقة مالية مستقلة (`FINANCE_APPROVAL`) لتغيير أرقام الاستقبال أو الرسوم أو تفعيل القنوات (AT-15). | لا يوجد تعارض. | تغيير رقم استقبال بنكي دون رقابة يوجه الأموال لجهة غير مصرحة؛ الضابط: المراجعة المزدوجة وعدم التفعيل قبل الاعتماد المالي. |
| **7. زر الإيقاف الفوري وسجل الرقابة (Kill Switch & Audit)** | التعطيل مقتصر على تغيير يدوي للقيمة في الذاكرة. | زر إيقاف فوري لأي منتج أو خدمة أو قناة دفع (`Kill Switch`) مع تسجيل فوري في جدول الرقابة (`AuditLog`) مع ذكر السبب ومنع أي عمليات جديدة مع الحفاظ على المعالجات الجارية (AT-24). | لا يوجد تعارض. | الضابط: إيقاف الطلبات الجديدة فوراً مع استمرار معالجة الطلبات السارية بأمان. |

### 2. خطة التنفيذ المعتمدة للمرحلة P06

1. **تحديث الحزم المشتركة وقاعدة البيانات:**
   - تحديث `packages/shared`: إضافة أنواع وتعدادات `ServiceRequestStatus`, `PriceRuleScope`, `MarginType`, `ChannelVerificationStatus`.
   - تحديث `packages/database/prisma/schema.prisma`: إضافة `ServiceRequest`, `PriceRuleVersion`, وحقول التحقق المالي والمراجعة المزدوجة في `PaymentChannelConfig` و`Product`.
2. **تطوير خدمات ومتحكمات الـ Backend:**
   - `CatalogAdminService` & Controller: إدارة الفئات، الخدمات، المنتجات، الحقول، وطلبات إضافة التطبيقات.
   - `PricingEngineService` & Controller: تطبيق هرمية الهوامش، حساب أسعار البيع، حفظ الإصدارات، وتوفير معاينة التسعير (`Pricing Preview`).
   - `PaymentChannelsAdminService`: إدارة القنوات والموافقة المالية المزدوجة والمفاتيح الطارئة (`Kill Switch`).
3. **تطوير واجهات المستخدم:**
   - `apps/web-admin`:
     - صفحة الكتالوج المطور وإدارة الخدمات والباقات والحقول الديناميكية.
     - صفحة محرك التسعير والهوامش مع المعاينة وإصدارات القواعد.
     - طابور مراجعة واعتماد طلبات إضافة التطبيقات للعملاء.
     - إدارة قنوات الدفع والاعتماد المالي المزدوج.
   - `apps/web-customer`:
     - نافذة / صفحة "طلب إضافة تطبيق أو باقة جديدة" للعملاء.
     - تحسين محرك البحث والتصفح والتوافق مع SEO.
4. **بناء وتشغيل حزم الاختبار الشاملة:**
   - كتابة اختبارات القبول الخاصة بالمرحلة: `AT-11`, `AT-12`, `AT-15`, `AT-22`, `AT-24`.
5. **تشغيل كافة خدمات المنصة:**
   - التأكد من تشغيل الـ Backend على المنفذ 4000، وWeb-Admin على 3001، وWeb-Customer على 3000 للفحص اليدوي.
6. **توثيق التقرير التنفيذي:**
   - إصدار `docs/PHASE_06_IMPLEMENTATION_REPORT.md`.
