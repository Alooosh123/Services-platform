# سياسات وضوابط الأمان (Security & Integrity Guidelines)
## حدود الطلبات ومقاومة التخمين

تستخدم المسارات الحساسة عدادات موزعة عبر Redis، بمفتاح مستقل لكل نطاق/مسار وعنوان IP، ويضاف معرف المستخدم عند توفره. النوافذ الحالية (لكل دقيقة):

- **المصادقة:** التسجيل 3، دخول العميل 5، تجديد الجلسة 20، دخول الإدارة 5، تحقق MFA للإدارة 5.
- **التحقق والاعتماد:** إرسال OTP للهاتف 3، التحقق من OTP 5، تفعيل MFA 5، إعداد رمز المعاملة 5، إنشاء موظف 5، تسجيل الخروج 10، إلغاء جميع الجلسات 3.
- **العميل والطلبات:** التحقق من اللاعب 20، Checkout 10، إنشاء طلب إيداع 5، إنشاء تذكرة دعم 5، رد العميل على التذكرة 20.
- **العميل والدفع والسحب:** إنشاء بطاقة/USDT 5، Webhook Stripe/USDT 600، طلب سحب 5.
- **العمليات الإدارية والمالية:** تنفيذ يدوي للطلب 10، استرداد الطلب 5، إعادة المحاولة 5، مراجعة الإيداع 20، اعتماد/رفض الإيداع 10، تجميد/رفع تجميد المحفظة 10، تأكيد الإيداع 10، تمويل المورد 5، اعتماد/تنفيذ/تأكيد يدوي/رفض السحب 5/5/5/10.
- **إعدادات القنوات والمزودين:** تغيير وضع القناة 10، التحويل الاحتياطي 5، إنشاء/اقتراح قناة أو حساب 5، اعتماد المالية 5، الإيقاف الطارئ 10، تحديث إعداد المزود 10، اختبار اتصال المزود 5.
- **التقارير والمالية:** إغلاق اليوم 3، تعديل إغلاق اليوم 5، إنشاء مستفيد أرباح 5، طلب/اعتماد/تأكيد سحب أرباح المالك 3/5/5.
- **الدعم والمطابقة:** إنشاء تذكرة 5، رد العميل 20، تغيير حالة/تعيين/ملاحظة دعم 20، مراجعة نزاع 5، تشغيل المطابقة 3، طلب معالجة فرق 5.
- **الإيداع التجريبي المباشر:** محاولتان، ومتاح للاختبارات الآلية فقط؛ محظور في التشغيل العادي.

يطبق Redis العملية ذرياً مع انتهاء صلاحية العداد. عند تجاوز الحد يعيد الخادم `429 Too Many Requests` ورأس `Retry-After`. عند تعذر Redis تُرفض المسارات المحددة برسالة `503` بدلاً من تعطيل الحماية أو التحول إلى عداد ذاكرة محلي.

**منع التكرار عبر HTTP:** نقطة `POST /api/orders/checkout` وحدها تفرض حالياً رأس `Idempotency-Key`، ويجب أن يطابق حرفياً `body.idempotencyKey`. لا تُفرض هذه الترويسة بصورة عامة على كل مسارات POST؛ فكل عملية أخرى تستخدم قيود التكرار الخاصة بها، ولا تُضاف إليها حماية HTTP إلا عند تهيئة العقد واختبارات العميل لها.

### 1. مبادئ النزاهة المالية والحماية من التلاعب

#### 1.1 قاعدة توازن دفتر الأستاذ الصارمة (Strict Double-Entry Invariance)
* يُحظر تماماً إجراء أي تعديل مباشر على حقل الرصيد (`balance = balance + amount`).
* كل حركة مالية يجب أن تكون قيداً محاسبياً متوازناً (`Total Debit == Total Credit`).
* تُنفذ عمليات القيود المالية المزدوجة داخل معاملات قاعدة البيانات بمستوى عزل `Serializable` أو `ReadCommitted` مع قفل الصفوف الحصري لمنع حدوث التزامن المتضارب (`Race Conditions`).
* لا يمكن لأي رصيد أن يصبح سالباً؛ يُرفض القيد فورياً إذا تجاوزت الخصومات الرصيد المتاح.

#### 1.2 مفاتيح منع التكرار (Idempotency Keys)
* نقطة `POST /api/orders/checkout` تتطلب ترويسة `Idempotency-Key` وتتحقق من تطابقها حرفياً مع `body.idempotencyKey`. لا تُفرض الترويسة حالياً على جميع عمليات الدفع والسحب؛ يجب ألا يُذكر أي مسار آخر على أنه محمي بهذا الـInterceptor إلا بعد إضافة العقد واختبارات العميل والخادم له.
* إذا أرسل العميل نفس المفتاح مرة أخرى بسبب انقطاع الاتصال أو بطء الشبكة:
  * يكتشف النظام المفتاح المسجل مسبقاً.
  * يُرجع النتيجة السابقة المخزنة مباشرة دون إعادة خصم المبلغ أو تنفيذ الشحن مرتين.

#### 1.3 حظر التعديل أو الحذف (Immutability & Reversals)
* سجلات المعاملات المالية المعتمدة (`LedgerTransaction`, `LedgerEntry`) غير قابلة للحذف أو التعديل برمجياً.
* في حال تصحيح خطأ أو إلغاء طلب:
  * يُنشأ قيد عكسي بنوع `REVERSAL`.
  * تُعكس الحسابات وتبقى المعاملة الأصلية مسجلة وموثقة مع ربط المعاملة العكسية بها `reversalOfId`.

### 2. التحكم في الوصول والصلاحيات (Role-Based Access Control - RBAC)

تُطبق المنصة نموذج التحقق متعدد الطبقات باستخدام حراس NestJS (`JwtAuthGuard` + `RolesGuard`):

| الدور | العمليات المسموح بها | العمليات المحظورة |
|---|---|---|
| `OWNER` | كافة العمليات، إنشاء المشرفين، إدارة السياسات المالية. | لا توجد. |
| `FINANCE_MANAGER` | اعتماد إشعارات الدفع، تسوية الأرصدة، عكس القيود، تقارير الأرباح. | تعديل إعدادات الخادم البرمجية. |
| `GENERAL_MANAGER` | إدارة المنتجات، تعديل أسعار البيع والتكلفة، مراقبة الطلبات. | السحب المالي المباشر بدون قيود مزدوجة. |
| `FULFILLMENT_OPERATOR` | تزويد أكواد الشحن اليدوية، تحديث حالة التنفيذ للطلبات. | اعتماد إشعارات المحافظ أو إجراء تسويات مالية. |
| `SUPPORT` | استعراض تذاكر الدعم والبحث في بيانات الطلبات بموافقة العميل. | تعديل أي أسعار أو إجراء أي عمليات مالية. |
| `AUDITOR` | استعراض كشوفات الأستاذ المالي وسجلات التدقيق للقراءة فقط. | كتابة أو تعديل أي سجلات. |
| `CUSTOMER` | استعراض الكتالوج، شحن المحفظة، الشراء، متابعة طلباته فقط. | الوصول لأي واجهة إدارية أو بيانات مستخدمين آخرين. |

### 3. تدقيق النظام وسجلات التتبع (Audit Logging)

* جدول `audit_logs` يسجل تلقائياً كل عملية حساسة تجري على النظام تشمل:
  * هوية المستخدم ورتبته (`userId`, `userRole`).
  * نوع الإجراء (`action` مثل `SYSTEM_INITIALIZATION`, `LEDGER_ADMIN_ADJUSTMENT`, `PROVIDER_DISPATCH_ORDER`).
  * اسم ونطاق الكيان المتأثر (`entityName`, `entityId`).
  * القيم القديمة والقيم الجديدة بتنسيق JSON (`oldValues`, `newValues`).
  * عنوان الإنترنت وعميل المتصفح (`ipAddress`, `userAgent`).
  * الطابع الزمني الموثق بدقة الميلي ثانية (`createdAt`).

### 4. حماية بيانات الدفع والاتصال

1. **تجزئة كلمات المرور:** استخدام مكتبة `bcrypt` بعدد دورات تمليح (Salt Rounds = 10).
2. **رموز المصادقة:** استخدام `JSON Web Tokens (JWT)` مشفرة بمفتاح سري آمن مع صلاحية محددة وفصل صريح بين رمز الوصول (`accessToken` صالح لمدة يوم) ورمز التجديد (`refreshToken` صالح لمدة 7 أيام).
3. **تطهير المدخلات (Input Sanitization):** تفعيل `ValidationPipe` مع `whitelist: true` و`forbidNonWhitelisted: true` لمنع حقن المعاملات الضارة.
4. **التحقق من صحة مدخلات اللاعب:** فحص الآيدي والسيرفرات بالتعبيرات النمطية الصارمة (`Regex`) لمنع هجمات الحقن النصي في حقول الشحن.

### 5. طبقة الأمان المركزية

* `SecurityCoreModule` يوفر `EncryptionService` لتشفير النصوص وJSON باستخدام AES-256-GCM مع IV ووسم مصادقة مستقلين لكل عملية. المفتاح `ENCRYPTION_KEY` يجب أن يكون 32 بايت ممثلة بـ64 خانة hex؛ لا تخزن المفتاح في قاعدة البيانات.
* بيانات اعتماد مزودي الخدمة الجديدة تُحفظ في `Provider.credentialsCiphertext`، ولا يعاد ciphertext في واجهات الإدارة. يلزم إعادة حفظ بيانات الاعتماد القديمة التي كانت مخزنة كنص صريح لنقلها إلى التشفير.
* تواقيع Webhook تستخدم `HMAC-SHA256` على البايتات الخام للطلب بالصيغة `HMAC(secret, timestamp + "." + rawBody)`، وتُرسل عبر `x-webhook-timestamp` و`x-webhook-signature`. تُرفض التواقيع التي يتجاوز عمرها خمس دقائق. يجب ضبط `WEBHOOK_HMAC_SECRET` بقيمة عشوائية مستقلة لا تقل عن 32 بايت.
* `IdempotencyInterceptor` مفعل حالياً على `POST /api/orders/checkout` فقط. يخزن علامة المعالجة والنتيجة في Redis لمدة 24 ساعة، ويرفض المفتاح نفسه إذا استُخدم لحمولة مختلفة. يجب على العميل إرسال `Idempotency-Key` مطابقاً تماماً لقيمة `body.idempotencyKey`. لا تُعمّم هذه الحماية على POST أخرى قبل توثيق العقد وتغطيتها باختبارات تكامل.
* يتطلب التشغيل الإنتاجي Redis متاحاً؛ فشل Redis لا يتحول إلى نجاح وهمي ولا يسمح بتنفيذ العملية دون قفل التكرار.
* `SensitiveAuditInterceptor` يسجل نتيجة الطلبات الحساسة وهوية المستخدم وعنوان IP وUser-Agent. لا ينسخ بيانات الطلب أو الأسرار إلى سجل التدقيق.

### 6. الجلسات والمصادقة المالية

* كلمات المرور الجديدة تُخزن باستخدام Argon2id. كلمات المرور القديمة بصيغة bcrypt تُحدّث تلقائياً إلى Argon2id بعد تسجيل دخول صحيح.
* Access Token صالح لمدة 15 دقيقة، وRefresh Token صالح لمدة 7 أيام؛ تحفظ Redis بصمة SHA-256 لرمز التحديث فقط، وتدعم تدوير الرمز وإبطال جلسات المستخدم.
* أسرار TOTP الجديدة تحفظ مشفرة عبر AES-256-GCM. أسرار TOTP القديمة غير المصدّرة تبقى قابلة للقراءة مؤقتاً حتى إعادة إعدادها.
* إعداد Transaction PIN يتطلب كلمة مرور الحساب، ويُخزن PIN مجزأً بـArgon2id. نقاط الشراء وتبادل العملات تتطلب `x-transaction-pin`؛ خمس محاولات خاطئة تقفل التحقق لمدة 15 دقيقة.
* أدوار الشراء وتبادل العملات محددة عبر `PoliciesGuard` بالإضافة إلى `RolesGuard`، وتأكيد الشراء/التبادل لا يعتمد على بيانات الدور الواردة من العميل.
