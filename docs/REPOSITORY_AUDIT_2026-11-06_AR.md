## 1. الخلاصة التنفيذية

المستودع يحتوي على أساس تقني معتبر: Backend بـ NestJS، متجرين Next.js، مخطط PostgreSQL/Prisma يتضمن نماذج مالية وSaaS، وواجهات Flutter. لكن لا يصح وصف النظام في وضعه الحالي بأنه مكتمل وجاهز للإطلاق التجاري؛ هناك أجزاء عرض تجريبي ومسارات غير دائمة، كما أن بوابة CI لم تكن تثبت البناء والاختبارات بالشكل الصحيح، ولا يوجد نشر إنتاجي حقيقي موصول.

أهم موانع الإطلاق الحالية:

1. واجهات إدارة SaaS كانت غير محمية على مستوى Controller، كما أن عمليات المستأجرين والاشتراكات والفواتير كانت تعتمد على مصفوفات ذاكرة داخل العملية بدل التخزين الدائم.
2. تطبيق Flutter كان يعرض نجاح شحن بعد تأخير زمني فقط، ويعرض اسم تحقق ورصيداً وسجل طلبات ثابتة دون طلب API.
3. بيانات seed تضمنت كلمات مرور افتراضية معلومة، وأرقام استقبال دفع غير مثبتة كانت تنشأ كقنوات نشطة.
4. ملف CI كان يخفي فشل `npm audit`، كما كان ينقصه بناء الحزمة المشتركة قبل الاختبارات ومتغير قاعدة البيانات قبل Prisma validation.
5. مهام staging وproduction في workflow كانت تطبع رسائل `echo` فقط ولا تنفذ نشرًا أو فحص صحة حقيقيًا.
6. أظهر تدقيق الاعتماديات في تشغيل 6 نوفمبر 2026 عدد **42 ثغرة**: 11 منخفضة، 15 متوسطة، 14 عالية، و2 حرجة.

## 2. أدلة من المستودع

### 2.1 SaaS وبيانات المستأجرين

- النماذج `SaaSPlan` و`SaaSTenant` و`SaaSSubscription` و`SaaSInvoice` موجودة في `packages/database/prisma/schema.prisma`.
- في المقابل، خدمة `apps/backend/src/modules/saas/saas.service.ts` كانت تعتمد على `inMemoryPlans` و`inMemoryTenants` و`inMemoryInvoices`. مراجعة الخدمة لم تجد استخداماً فعلياً لـ `saaSTenant` أو إنشاء سجلات المستأجرين والاشتراكات والفواتير في Prisma.
- صفحة `apps/web-saas/src/app/page.tsx` واجهة ثابتة مختصرة، وليست لوحة SaaS تشغيلية متكاملة.
- Controller الخاص بـ SaaS لم يكن يطبق الحراس التي كانت مستوردة في الملف.

### 2.2 تطبيق الهاتف

في `apps/mobile-customer/lib/main.dart` كانت واجهة الشحن تؤخر النتيجة 800ms ثم تعرض نجاحاً، دون استدعاء خادم أو مزود. وكان زر التحقق يحول الحالة محلياً إلى `Gamer_Verified`. كما احتوت الشاشة على رصيد وسجل طلبات ثابتين.

يوجد أيضاً مسار Flutter آخر في `mobile-customer/` بجانب `apps/mobile-customer/`. يجب حسم التطبيق الذي سيُعتمد للإصدار، وتوحيد المصدر قبل تجهيز المتاجر.

### 2.3 CI/CD ونتائج التشغيل

مرجع آخر تشغيل فُحص: [GitHub Actions run #42276306663](https://github.com/Alooosh123/Services-platform/actions/runs/42276306663).

- مهمة Backend tests فشلت في 28 مجموعة اختبار بسبب عدم بناء `@digital-topup/shared` قبل تشغيل Jest، وظهر الخطأ `Cannot find module '@digital-topup/shared'`. خمس مجموعات فقط وصلت إلى التنفيذ بنجاح في ذلك التشغيل.
- مهمة Prisma validation فشلت لغياب `DATABASE_URL` في بيئة المهمة.
- خطوة التدقيق كانت تستخدم `npm audit --audit-level=high || true`، أي أنها كانت تخفي حالة الفشل.
- سجل `npm ci` في التشغيل نفسه 42 ثغرة (التوزيع مفصل أعلاه).
- مهام النشر كانت رسائل `echo` لا تنفذ أي اتصال بخادم أو اختبار endpoint فعلي.

هذه نتائج تشغيل قديم على `main`؛ يجب استخدام تشغيل PR الجديد للتحقق من التعديلات الموجودة في هذا الفرع. لم يتم الادعاء هنا بأن الاختبارات الجديدة نجحت قبل ظهور نتيجتها.

### 2.4 النشر والبنية التحتية

- لا يوجد `docker/docker-compose.prod.yml` في المستودع؛ الموجود `docker/docker-compose.yml` معد للتشغيل المحلي ويشغّل PostgreSQL وRedis والتطبيقات.
- لا يوجد في workflow إعداد نشر متصل بمضيف إنتاج أو تشغيل فحوص صحة واستعادة فعلية.
- صفحة SaaS ومكونات الهاتف والتكاملات تحتاج إكمالاً قبل اعتبار المنصة متعددة المتاجر وجاهزة للتجارة.

### ملاحظات مهمة عن التغييرات

- منع استخدام مخازن SaaS داخل الذاكرة في production هو **حاجز أمان مؤقت** وليس تنفيذاً كاملاً لتعدد المستأجرين. المطلوب لاحقاً توصيل جميع عمليات SaaS بـ Prisma transactions وإضافة عزل Tenant فعلي واختبارات صلاحيات وعزل بين متاجر مختلفة.
- إزالة نجاح الشحن الوهمي تمنع الادعاء بتنفيذ عملية لم تحدث؛ لكنها لا تكمل اتصال Flutter بالخادم.
- التدقيق الأمني أصبح يفشل بوضوح عند وجود ثغرات High/Critical. لذلك من المتوقع أن تظل بوابة الجودة حمراء إلى أن تتم معالجة الاعتماديات والتحقق من التوافق، ولا يجوز استخدام `npm audit fix --force` دون مراجعة breaking changes.
- تعطيل القنوات يعتمد على seed لقاعدة جديدة أو إعادة ضبط تطويرية. القنوات الموجودة مسبقاً في قاعدة قائمة لا تتغير تلقائياً بهذه التعديلات، ويجب مراجعتها وتعطيل غير المعتمد منها يدوياً قبل أي تشغيل تجاري.

## 4. ما لم يكتمل بعد — موانع إطلاق صريحة

1. **SaaS persistence:** تحويل الخطط والمستأجرين والاشتراكات والفواتير إلى CRUD حقيقي ودائم باستخدام Prisma، مع معاملات ذرية وتاريخ تدقيق.
2. **Tenant isolation:** إضافة tenant context إلى الطلبات والبيانات، وتطبيق العزل على كل استعلام وخدمة وملف وصلاحية، واختبارات تمنع وصول متجر إلى بيانات متجر آخر.
3. **SaaS Web:** تطوير لوحة Super Admin فعلية بدلاً من الصفحة الثابتة وربطها بالـ API المحمي.
4. **Flutter:** اختيار المسار الرسمي، إضافة تسجيل الدخول والتخزين الآمن، API client، wallet/orders/catalog، حالات الخطأ، ومنع أي إجراء مالي محلي.
5. **المزودون وقنوات الدفع:** لا توجد في هذا التدقيق أدلة كافية على مفاتيح إنتاج وعقود API وعمليات تسوية حقيقية. يجب استخدام بيانات تعاقدية يقدمها المالك، وإبقاء Mock منفصلًا عن production.
6. **الأسعار والعملات:** أسعار الصرف الموجودة في seed قيم مرجعية تاريخية وليست مصدراً حياً؛ يجب عدم اعتبارها أسعار تشغيل دون اعتماد مالي حديث. يجب منع أي تحويل ضمني.
7. **الأمن:** معالجة الثغرات الـ42، مراجعة Next.js/NestJS ومكتبات الرفع والاعتماديات العابرة، وفحص الأسرار في تاريخ Git، وتدوير أي قيمة سرية حقيقية أو أعيد استخدامها.
8. **النشر:** إنشاء Compose إنتاجي فعلي، مضيف وخدمة DNS ونطاقات فرعية، TLS، إدارة أسرار، شبكة داخلية لقواعد البيانات، مراقبة وتنبيهات، ونسخ احتياطي مشفر خارج الخادم مع تجربة استعادة موثقة.
9. **الاختبارات التشغيلية:** تشغيل حمل متزامن، اختبارات اختراق مستقلة، فحص عدم تكرار الخصم، مطابقة Ledger، وتجربة استعادة ببيانات مالية اختبارية متوازنة.
10. **الإطلاق التجاري:** مفاتيح المتاجر وحسابات Google Play/Apple إن كان التطبيق سيُنشر عليهما، مستندات قانونية وسياسات، تجارب Beta وموافقة المالك.

## 5. الخطوات اليدوية المطلوبة من مالك المشروع

لا تُرسل كلمات مرور أو مفاتيح API في محادثة GitHub أو في ملفات المصدر. جهّزها مباشرة في Secret Manager الخاص بالاستضافة أو GitHub Actions بعد تحديد النشر.

1. إنشاء ملف محلي `.env` من `.env.example` وتغيير كل placeholders إلى أسرار خاصة، وتحديد كلمات مرور seed التطويرية محلياً فقط.
2. تزويد مسؤول المالية بأرقام الاستقبال الرسمية لكل من جيب وجوالي وكاش وون كاش ومحفظة إيزي، مع اسم المستفيد وإثبات الملكية؛ تظل القنوات معطلة إلى أن يعتمدها مسؤول المالية.
3. اعتماد أسعار الصرف وسياسة الرسوم لكل عملة من مصدر مالي موثوق وتحديد من يملك صلاحية تغييرها.
4. توفير عقود ومفاتيح بيئة Sandbox/Production الرسمية لمزودي شحن الألعاب وقنوات الدفع، دون إرسالها في نص المحادثة.
5. تحديد نطاقات الدومين والخادم ومزود الاستضافة ومسؤول النسخ الاحتياطية.
6. تحديد المسار النهائي لتطبيق Flutter؛ يوجد حالياً مساران متوازيان ويجب توحيد المصدر.

**تنبيه قاعدة البيانات:** لا تضبط `RESET_DATABASE_SEED=true` على قاعدة بيانات قائمة؛ هذا الخيار يحذف بيانات تطويرية. كما أن تغيير بيانات seed لا يعدّل سجلات قنوات الدفع الموجودة سابقاً تلقائياً.
