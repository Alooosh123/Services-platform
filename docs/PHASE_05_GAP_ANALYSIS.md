## 1. جدول مقارنة الوضع الراهن والمستهدف (Gap Analysis Matrix)

| المكون / المتطلب | الوضع الحالي في الكود (EXISTING) | النواقص البرمجية (MISSING) | التعارضات والمحاذير (CONFLICT) | المخاطر والقيود (RISKS & BLOCKED) |
| :--- | :--- | :--- | :--- | :--- |
| **1. قدرات محولات قنوات الدفع (PaymentChannelAdapter Capabilities)** | `IPaymentChannelAdapter` يحتوي فقط على `validateTransfer` و `getInfo` و `getChannelCode` | أعلام القدرات المنفصلة: `depositConfirm`, `transactionLookup`, `payout`, `balance`, `reconcile`. التبديل بين `MANUAL` و `API`. | عدم كسر المحولات الحالية (`Jaib`, `Jawali`, `Cash`, `OneCash`, `Easy`). | البنوك اليمنية لا توفر واجهات Payout مفتوحة دون عقود B2B خاصة؛ يجب وسم الميزات غير المتاحة بـ `BLOCKED_EXTERNAL`. |
| **2. الويب هوك والإيداع الآلي (Inbound Webhook & Idempotency)** | الإيداع يعتمد كلياً على المراجعة اليدوية (`MANUAL_VERIFY`) عبر رفع صورة السند والموافقة البشرية | نقطة استقبال الويب هوك `POST /api/deposits/webhook/:channel`، فحص التوقيع الرقمي، تطابق المرجع والمبلغ والعملة، ومنع تكرار الإيداع (`Idempotency`). | يجب ألا يؤدي الويب هوك إلى تجاوز القيود المحاسبية أو التغذية العشوائية دون قيد متوازن. | احتمال وصول إشعارات وهمية أو غير متطابقة؛ يجب حجر المبالغ غير المتطابقة ومنع الاعتماد التلقائي. |
| **3. الرصيد التجاري للمزود (Supplier Balance & Gating)** | جدول `Provider` يحتوي على حقل `balance` و `FulfillmentService` يسجل تكلفة البضاعة المباعة فقط بعد النجاح | خدمة إدارة الرصيد التجاري `SupplierBalanceService`، شحن رصيد المزود مسبقاً، وفحص كفاية الرصيد قبل تفويض الشحن (*Fulfillment Gating*). | الخلط بين تكلفة تنفيذ الطلب (*Fulfillment Cost*) وحركة السيولة النقدية (*Cash Movement*). | نفاد رصيد المنصة لدى المزود قد يسبب فشل الشحن؛ يجب تحويل الطلب إلى `ManualReview` مع تنبيه مالي. |
| **4. سحب الأرباح والتحويل الخارجي (Payout Requests & Safety)** | لا يوجد مسار سحب أرباح أو تحويل مالي خارجي في الـ Backend | مسار `PayoutService` لإدارة طلبات السحب بدورات: `REQUESTED` → `APPROVED` → `SENT` → `CONFIRMED` / `FAILED` / `UNKNOWN`. | خطر السحب المضاعف عند بطء الشبكة أو انقطاع الاتصال مع البنك. | عدم توفر API رسمي للمصارف اليمنية لصرف الحوالات آلياً؛ يجب وسم الـ Auto-Payout كـ `BLOCKED_EXTERNAL` واعتماد مسار التحويل اليدوي المؤكد. |
| **5. التسوية اليومية ومطابقة الحسابات (Daily Reconciliation Batch)** | تقارير مبيعات فقط في `ReportsService` دون مطابقة كشوف الحسابات | محرك التسوية الثلاثي `ReconciliationService`، كشف الفروقات (*Discrepancies*)، وطابور معالجة الحالات المجهولة (*Unknown Items & Disputes*). | تباين توقيت تسجيل العمليات بين كشف البنك والنظام الداخلي. | عدم تطابق الكشوف يسبب فجوة في رأس المال العامل؛ إيقاف إعادة المحاولات الآلية للعمليات المتنازع عليها. |
| **6. لوحة إدارة التسوية (Reconciliation Dashboard)** | لوحات لإدارة الطلبات والإيداعات ودفتر الأستاذ والتدقيق فقط | صفحة خاصة للتسوية والمطابقة `/reconciliation` في `web-admin` لعرض الدفعات اليومية والاستثناءات وتأكيد المطابقة. | الحفاظ على التصميم المتناسق لـ Web Admin وسرعة الاستجابة. | سهولة استخدام لوحة المشغل المالي للتدقيق والمطابقة اليدوية. |

## 2. مصفوفة حالات الاعتماد للمزودين (External Integration Status)

```
[القنوات والخدمات]
├── الويب هوك واستلام الإيداعات:
│   ├── وضع المحاكاة والاختبار (Sandbox/Mock): مدعوم ومكتمل لاختبار التكرار وتطابق المبالغ.
│   └── القنوات البنكية الحقيقية (Jaib, Jawali, Cash): BLOCKED_EXTERNAL (تعتمد على تدفق MANUAL_VERIFY لحين توقيع اتفاقيات الربط الآلي).
├── الصرف والسحب الخارجي (Outbound Payout):
│   └── التحويل الآلي المباشر: BLOCKED_EXTERNAL (يتم عبر مسار الإجراء المالي اليدوي المعتمد SOP مع توثيق السند والقيد المحاسبي).
└── الرصيد التجاري للمزودين (Supplier Balance):
    ├── تتبع الرصيد الداخلي والحد الائتماني: مدعوم ومفعل بالكامل (ACTIVE_INTERNAL).
    └── استعلام الرصيد الآلي عبر API المزود: مدعوم للشركاء المزودين بـ API، وموسوم بـ BLOCKED_EXTERNAL للمزودين اليدويين.
```

## 3. خطة العمل المعتمدة لتنفيذ P05

1. **تحديث الحزم المشتركة وقاعدة البيانات (`packages/shared` & `packages/database`):**
   - إضافة حالات الدفع والتحويل والتسوية: `PayoutStatus`, `ReconciliationStatus`, `DiscrepancyType`.
   - دعم نماذج `PayoutRequest`, `ReconciliationBatch`, `ReconciliationItem`, `SupplierAccount` في الذاكرة ومخطط البيانات.
2. **تطوير محولات القنوات والويب هوك (`PaymentChannelAdapter` & Inbound Webhooks):**
   - إضافة مصفوفة القدرات `capabilities` لكل محول مع دعم التبديل الآمن.
   - برمجة معالج الويب هوك الآمن مع فحص التوقيع، التحقق الصارم من تطابق المبلغ والعملة والمرجع، ومنع التكرار التام (`Idempotency`).
3. **تطوير خدمة الرصيد التجاري للمزودين (`SupplierBalanceService`):**
   - تسجيل حركات شحن الرصيد التجاري للمزود منفصلة عن قيود التكلفة اليومية.
   - حراسة أوامر الشحن (*Fulfillment Gating*)؛ تعليق الطلب إذا كان رصيد المزود غير كافٍ.
4. **تطوير محرك التسوية والمطابقة الثلاثية (`ReconciliationService`):**
   - مطابقة كشوف الحسابات ↔ الإيداعات/المسحوبات ↔ قيود الدفتر المالي ↔ تكاليف الشحن.
   - كشف الفروقات وتوجيه العمليات المجهولة لطابور التدقيق اليدوي.
5. **تطوير خدمة السحب المالي (`PayoutService`):**
   - إدارة طلبات سحب الأرباح مع التحقق من الصلاحيات والـ MFA والحدود المالية، ومنع السحب المزدوج.
6. **بناء واجهات المشرف الإداري في `web-admin`:**
   - شاشة التسوية والمطابقة اليومية (`/reconciliation`) مع فلاتر الاستثناءات ونافذة معالجة الفروقات.
7. **كتابة الاختبارات الشاملة (Unit & Integration Tests):**
   - اختبارات AT-16 (دفع تكلفة المزود من الرصيد التجاري).
   - اختبارات AT-18 (فشل وتكرار السحب دون خصم مضاعف).
   - اختبار منع إضافة الرصيد مرتين عند تكرار الويب هوك (*Webhook Idempotency*).
   - اختبار رفض الاعتماد الآلي عند عدم تطابق المرجع أو المبلغ أو العملة.
   - اختبار التبديل الآمن للقناة إلى الوضع اليدوي عند انقطاع الاتصال.
8. **التوثيق وإصدار تقرير التسليم:**
   - كتابة `docs/PHASE_05_IMPLEMENTATION_REPORT.md` وتحديث `docs/PROJECT_STATUS.md`.
