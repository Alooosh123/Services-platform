# دليل النسخ الاحتياطي والاستعادة — MySQL 8.4 + Podman

## المسار المعتمد

قاعدة التشغيل المستهدفة هي MySQL 8.4 LTS (InnoDB). التشغيل المحلي يستخدم Podman Desktop + Podman Compose. يتطلب تنفيذ النسخ والاستعادة توفر عميل MySQL 8.4 على المضيف، أو تفعيل وضع عميل Podman الموثق في متغيرات البيئة عند استخدامه.

لا ترفع ملفات النسخ أو مفاتيح التشفير إلى Git أو نظام التذاكر. تُنشأ النسخة بصيغة SQL مشفرة بـ AES-256-GCM، ويُنشأ بجانبها ملف SHA-256 للتحقق من سلامة الملف.

## إنشاء نسخة MySQL مشفرة

تأكد أولاً أن .env يحتوي DATABASE_URL وBACKUP_ENCRYPTION_KEY بقيمة خاصة مكونة من 64 خانة hexadecimal. احتفظ بمفتاح التشفير في Secret Manager منفصل عن مخزن النسخ.

```powershell
npm run db:backup
```

يجب توفر الأمر mysqldump من MySQL 8.4 Client في PATH. تُحفظ النسخ افتراضياً داخل backups/ أو في المسار المحدد بواسطة BACKUP_DIR. لا تحذف الأداة النسخ القديمة تلقائياً؛ طبّق سياسة احتفاظ ونسخ خارج الجهاز مع تشفير النقل والتخزين.

## استعادة اختبارية معزولة

أنشئ قاعدة MySQL فارغة مستقلة عن قاعدة المصدر باسم يحتوي restore أو test أو sandbox. اضبط RESTORE_DATABASE_URL إليها، واحفظ BACKUP_ENCRYPTION_KEY نفسه المستخدم وقت إنشاء النسخة.

```powershell
$env:NODE_ENV = "test"
$env:RESTORE_DATABASE_URL = "mysql://restore_user:secret@127.0.0.1:3306/digital_topup_restore"
npm run db:restore -- --file "backups\mysql_<timestamp>.dump" --confirm-restore
```

ترفض الأداة أسماء قواعد الإنتاج، وهدف الاستعادة نفسه كقاعدة المصدر، وقاعدة الهدف غير الفارغة، والاتصال البعيد افتراضياً. تتحقق من SHA-256 ومن وسم المصادقة AES-256-GCM قبل فك التشفير، ولا تحذف جداول قائمة ولا تنفذ DROP DATABASE. لا تفعّل ALLOW_REMOTE_RESTORE=true إلا لتمرين استعادة معزول ومراجع.

## التحقق بعد الاستعادة

لا يكفي وجود الجداول كدليل نجاح. بعد كل تمرين استعادة:

1. تحقق من حالة Prisma migrations ومن تطابق عدد الجداول.
2. قارن عدد الصفوف والبصمات للبيانات المرجعية والجداول التشغيلية.
3. طابق مجموع المدين والدائن لكل عملة على حدة، وتأكد من عدم تعديل أرصدة المحافظ مباشرة.
4. تحقق من الطلبات والإيداعات والمدفوعات المعلقة ومراجع idempotency ومخزون PIN.
5. سجّل زمن الاستعادة ووقت آخر نسخة ناجحة واحسب RTO/RPO الفعليين.

## الانتقال من PostgreSQL

أوامر المصدر القديم محفوظة مؤقتاً بشكل منفصل:

```powershell
npm run db:backup:postgres
npm run db:restore:postgres -- --file "<source-backup>" --confirm-restore
```

تستخدم هذه الأدوات فقط لاستخراج/استعادة نسخة المصدر PostgreSQL في بيئة معزولة أثناء مشروع التحويل. لا تعتبر أي نسخة PostgreSQL دليلاً على نجاح نقل البيانات إلى MySQL. يلزم ETL ومقارنة صفوف ومطابقة مالية موثقة، ثم موافقة المالك والمالية قبل تغيير اتصال الإنتاج.

## حالة الإثبات

وجود الأدوات والـ CI لا يعني أن بيانات الإنتاج نُقلت أو أن استعادة إنتاجية تمت. حتى يتم تشغيل تمرين فعلي ببيانات اختبار ذات حجم مماثل وتسجيل نتائجه، تبقى حالة RTO/RPO ونجاح الاستعادة الإنتاجية غير معتمدة. لا تستخدم هذه الأدوات لاستعادة قاعدة الإنتاج.
