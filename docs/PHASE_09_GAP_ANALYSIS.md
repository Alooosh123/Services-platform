## 1. مرجعية المتطلبات والمعايير (Requirements Reference)

| الرمز | المرجع في خارطة الطريق | المتطلب الأساسي والضوابط |
| :--- | :--- | :--- |
| **AT-08** | Master Acceptance Tests | فحص دورة حياة رموز OTP (صحيح، خاطئ، منتهي، مكرر)؛ عامل حيازة تقني فقط؛ عمر 3 دقائق وقفل بعد 3 محاولات. |
| **AT-09** | Master Acceptance Tests | عزل مساعد الذكاء الاصطناعي (AI Risk Assistant) عن أي تحكم مالي مباشر أو تعديل في دفتر الأستاذ العام (Zero Ledger Impact). |
| **AT-19** | Master Acceptance Tests | حماية BOLA / IDOR الصارمة: منع أي تلاعب بمعرفات `WalletID` أو `OrderID` أو `PayoutID` وتسجيل محاولة الاختراق فوراً في سجل التدقيق الأمني. |
| **AR-02** | Architecture Requirements | التحقق الصارم من التوقيع الرقمي للويب هوك ومنع التكرار (Anti-Replay) ورفض الـ Callbacks المزورة. |
| **AR-06** | Architecture Requirements | ضوابط الرقابة الثنائية (Four-Eyes Principle) وفصل الصلاحيات في المعاملات المالية وتغيير الحسابات البنكية. |
| **AR-08** | Architecture Requirements | حماية الخصوصية وحق النسيان وتصدير البيانات وحذف الرموز المؤقتة دون المساس بإلزامية دفتر الأستاذ العام (Ledger Immutability). |
| **NFR-03** | Non-Functional Requirements | حماية الحسابات والأموال ضد الاستيلاء وهجمات تبديل الشرائح (SIM Swap) وتجميد المحافظ الإداري. |
| **NFR-07** | Non-Functional Requirements | الامتثال للحدود اليومية لمبالغ المعاملات وسرعة الطلبات (Velocity Limits). |

## 2. تحليل الوضع القائم مقابل الفجوات (Current State vs. Missing Gaps)

| المجال الأمني | المنجز حالياً (P01 - P08) | الفجوة المحددة في P09 | خطة المعالجة والتنفيذ |
| :--- | :--- | :--- | :--- |
| **1. حماية BOLA / IDOR (AT-19)** | حماية BOLA منفذة في بعض الـ controllers (مثل `Orders`, `Support`, `Notifications`). | لا توجد حزمة اختبارات اختراق شاملة وموحدة تؤكد حظر الوصول عبر كافّة الكائنات مع تسجيل حدث أمني `BOLA_VIOLATION_ATTEMPT` في `AuditLog`. | بناء فحص أمني شامل وتسجيل محاولات التلاعب بمعرفات المستخدمين في جدول الرقابة. |
| **2. عزل جلسات الموظفين والـ RBAC** | تم تحديد أدوار `UserRole` في النظام. | غياب اختبارات حاسمة تثبت عجز موظف الدعم (`SUPPORT`) أو المشغل (`OPERATOR`) عن اعتماد سحوبات مالية أو تجميد أرصدة أو الوصول لأرباح المالك. | كتابة سيناريوهات حظر الصلاحيات وتأكيد رجوع خطأ 403 Forbidden. |
| **3. مؤشرات تغيير الهاتف وSIM Swap** | تأكيد أرقام الهواتف اليمنية مع التحقق من المشغل في P04. | عند تحديث أو إعادة التحقق من رقم الهاتف، لا توجد فترة تبريد (Cooling-off Period - 24 ساعة) تعلق سحب الأموال لحماية المحفظة من هجمات الاستيلاء. | إضافة فحص `coolingOffPeriod` في خدمة السحوبات `PayoutsService` يمنع السحب لمدة 24 ساعة بعد إعادة التحقق من الرقم. |
| **4. مكافحة الاحتيال وحدود السرعة (Velocity Limits)** | التحقق من الرصيد والـ Idempotency Key. | غياب حدود لمعدل المعاملات المتتابعة السريعة (مثل أكثر من 5 طلبات في الدقيقة) أو حد أقصى للعملية الفردية بدون مراجعة. | إضافة محرك تدقيق سرعة الطلبات `FraudVelocityService` يعلق الطلبات المشبوهة للتدقيق البشري. |
| **5. تجميد المحافظ والتعامل مع الحسابات المشبوهة** | وجود حقل `isFrozen` في نموذج `Wallet` وفحصه في `LedgerService`. | غياب واجهات ولوحة تحكم رسمية للإدارة لتجميد وإلغاء تجميد المحافظ مع توثيق إلزامي للسبب وسجل تدقيق SOP. | إنشاء endpoints رسمية في لوحة الإدارة مع تسجيل تدقيق وإشعار للعميل. |
| **6. الخصوصية وحق النسيان وتصدير البيانات (AR-08)** | تخزين موافقات الربط `ConsentGrant`. | غياب مسار تصدير بيانات العميل (`Data Export`) ومسار طلب حذف الحساب مع الحفاظ على إلزامية عدم حذف قيود الأستاذ العام. | إنشاء وحدة `PrivacyModule` توفر تصدير بيانات المستخدم وحذف/تعمية البيانات الشخصية مع حماية دفتر الأستاذ. |
| **7. تنظيف الرموز المؤقتة المنتهية (Data Retention)** | رموز التحقق تنتهي زمنياً. | غياب مسار صيانة دوري لحذف رموز التحقق المنتهية والجلسات القديمة من قاعدة البيانات. | إنشاء خدمة تنظيف مجدولة `PurgeExpiredTokensService`. |
| **8. عزل الذكاء الاصطناعي التام (AT-09)** | محرك الذكاء الاصطناعي استشاري ولا يكتب في جدول القيود. | ضرورة إثبات ذلك باختبار اختراق حقيقي يثبت حظر استدعاء أي إجراء مالي للذكاء الاصطناعي وتطبيق مبدأ Least Privilege. | كتابة اختبار صريح يمرر مدخلات خبيثة وحقن أوامر ويثبت بقاء الأستاذ العام دون أي تغيير. |

## 3. خطة العمل المنهجية لتنفيذ المرحلة (Implementation Roadmap)

1. **الخطوة 1: طبقة البيانات والمشترك (`@digital-topup/shared`):**
   - إضافة أنواع وبيانات الخصوصية وتجميد المحافظ وسجلات الرقابة الأمنية (`PrivacyExportDto`, `WalletFreezeDto`, `FraudCheckResult`).
2. **الخطوة 2: وحدة الخصوصية والامتثال (`apps/backend/src/modules/privacy`):**
   - توفير مسار تصدير بيانات العميل (JSON).
   - توفير مسار حذف/تعمية الحساب مع فحص تصفية الرصيد والالتزامات أولاً ومنع حذف القيود المالية.
   - توفير مسار تنظيف الرموز المؤقتة المنتهية.
3. **الخطوة 3: إدارة تجميد المحافظ ومكافحة الاحتيال (`wallet` & `payouts`):**
   - إضافة مسارات `POST /api/wallets/:id/freeze` و `POST /api/wallets/:id/unfreeze` في لوحة الإدارة.
   - إضافة فحص فترة التبريد (Cooling-off Period) في خدمة السحوبات `PayoutsService` ضد استيلاء الهواتف (SIM Swap).
   - إضافة فحص سرعة الطلبات والحدود القصوى للعملية الفردية.
4. **الخطوة 4: حزمة اختبارات الاختراق والأمن الشاملة (`security-penetration.spec.ts`):**
   - اختبارات القبول AT-08 (دورة حياة OTP).
   - اختبارات القبول AT-09 (عزل AI التام عن الأستاذ).
   - اختبارات القبول AT-19 (فحص تلاعب BOLA/IDOR عبر مختلف الكائنات).
   - اختبارات فصل الصلاحيات للموظفين وسحب الأرباح.
   - اختبارات تزوير الويب هوك وتكراره.
   - اختبارات تجميد المحفظة وحظر العمليات.
   - اختبارات الخصوصية وحق النسيان.
5. **الخطوة 5: واجهة لوحة الإدارة الأمنية (`apps/web-admin/src/app/security/page.tsx`):**
   - لوحة رصد المحاولات الأمنية المشبوهة وتنبيهات BOLA.
   - إدارة تجميد المحافظ والرفع الإداري للحظر.
   - تنظيف الرموز المنتهية بنقرة زر واحدة.
6. **الخطوة 6: التوثيق الأمني المعتمد:**
   - تقرير التدقيق ونموذج التهديدات `THREAT_MODEL_SECURITY_REVIEW.md`.
   - تقرير اختبار الاختراق `PEN_TEST_REPORT.md`.
   - أدلة تشغيل الحوادث والاحتيال `INCIDENT_AND_FRAUD_RUNBOOKS.md`.
   - تقرير الإنجاز `PHASE_09_IMPLEMENTATION_REPORT.md`.
