# إجراءات التشغيل المالي لقنوات الدفع اليدوي

## 1. الوضع المعتمد

لا يوجد تكامل آلي مثبت مع جيب أو جوالي أو كاش أو ون كاش أو محفظة إيزي في هذا الفرع. جميع القنوات اليمنية الخارجية تعمل يدوياً فقط. لا تعرض المنصة رقم استقبال افتراضياً، ولا تمنح إيصال العميل وحده صفة إثبات نهائي. حسابات القنوات المزروعة في قاعدة البيانات تبدأ `NOT_CONFIGURED` و`PENDING_REVIEW` و`isActive=false`.

لا تستخدم قناة `API` حتى يوجد عقد/وثائق مزود ومفاتيح رسمية وبيئة اختبار وتوقيع Webhook واختبارات idempotency وreconciliation واعتماد إصدار مستقل. مسار الإعداد الحالي يمنع تحويل القنوات اليمنية إلى API.

## 2. تهيئة حساب استقبال لقناة

يلزم توافر مستند رسمي يثبت أن حساب الاستقبال يعود للمنشأة/صاحب الحساب المخول، واسم المستفيد ورقم الحساب والعملة والحدود والرسوم وتعليمات التحويل. لا تضع بيانات حساب شخصية قبل تحقق المالك والمالية.

1. يسجل موظف مخول طلب التغيير عبر `POST /api/admin/deposits/channels/{channel}/propose-account` ويرسل `accountNumber` و`feePercentage` عند الحاجة و`reason`.
2. تحفظ قاعدة البيانات رقم الحساب الجديد في حقل pending فقط، ويوقف ظهور القناة للعملاء أثناء المراجعة. يحفظ سجل التدقيق هوية مقدم الطلب ويعرض الرقم مقنّعاً.
3. يراجع Finance Manager أو General Manager أو Owner المستندات بشكل مستقل ويقرر عبر `POST /api/admin/deposits/channels/{channel}/finance-approval` مع `approved=true` و`financeNotes` أو `approved=false` وسبب رفض.
4. لا يسمح النظام لمقدم الطلب باعتماد طلبه. عند الموافقة، ينقل الرقم من pending إلى الرقم الفعّال ويضبط القناة `MANUAL` فقط. لا يتم تفعيل API.
5. تحقق من أن `GET /api/deposits/channels` يعرض القناة بعد التحقق وأن التعليمات والعملة وحدود المبالغ صحيحة قبل إعلانها للعملاء.

القنوات المعرفة حالياً تشمل `JAIB`, `JAWALI`, `CASH`, `ONE_CASH`, `EASY`. لا تنشئ قناة مكررة برمز قائم؛ استخدم طلب تغيير الحساب.

## 3. استلام طلب إيداع من العميل

1. يختار العميل قناة ظاهرة في `GET /api/deposits/channels` ويرسل `POST /api/deposits/request` مع العملة والمبلغ والرقم المرجعي وإثبات التحويل وبيانات المرسل حسب DTO.
2. يبدأ الطلب بحالة `PENDING`. تسجيل الطلب لا يضيف رصيداً للمحفظة ولا ينشئ قيداً محاسبياً.
3. يمنع تكرار الرقم المرجعي داخل القناة نفسها. احتفظ بملف الإثبات المرفق وفق سياسة حماية البيانات، ولا تسجّل كلمات مرور المحافظ أو رموز OTP.

## 4. التحقق اليدوي قبل الاعتماد

موظف المراجعة يفتح الطلب عبر `GET /api/admin/deposits/{id}` ثم يضعه في `UNDER_REVIEW` عبر `POST /api/admin/deposits/{id}/under-review`.

يلزم التحقق المستقل من تطبيق المحفظة/كشف الحساب الرسمي لدى صاحب الحساب، وليس من صورة العميل وحدها. طابق:

- رقم العملية المرجعي كما يظهر في سجل المحفظة الأصلي، لا نصاً يكتبه العميل فقط.
- اسم/رقم حساب المستفيد الذي وافقت عليه المالية.
- المبلغ والعملة والرسوم والمبلغ الصافي وتاريخ/وقت العملية.
- حالة العملية (ناجحة/مكتملة وليست معلقة أو ملغاة) وعدم استخدام المرجع لطلب سابق.
- هوية المحوّل عند وجود متطلبات امتثال داخلية، مع تقليل حفظ البيانات الحساسة.

عند عدم القدرة على التحقق أو وجود اختلاف: أبقِ الطلب في المراجعة أو ارفضه بسبب واضح. لا تعتمد عملية غير مؤكدة، ولا تعِد إرسال تحويل خارجي تلقائياً.

## 5. موافقة مستقلة وقيد الإيداع

بعد إثبات الاستلام، ينشئ موظف المالية الأول طلب موافقة:

```http
POST /api/operational-approvals
Content-Type: application/json

{
  "approvalType": "FINANCIAL_RECONCILIATION",
  "targetType": "DEPOSIT_REQUEST",
  "targetId": "<deposit-uuid>",
  "action": "CREDIT_VERIFIED_DEPOSIT",
  "reason": "تمت مطابقة العملية مع كشف المحفظة الرسمي ورقم المرجع والمبلغ والعملة."
}
```

يعتمد الطلب شخص مستقل مخوّل (Finance Manager أو General Manager أو Owner) عبر:

```http
POST /api/operational-approvals/{approvalId}/decision
Content-Type: application/json

{ "decision": "APPROVE", "notes": "تم التحقق المستقل من كشف الحساب." }
```

ثم ينفذ الموافق نفسه قيد الإيداع عبر:

```http
POST /api/admin/deposits/{depositId}/approve
Content-Type: application/json

{ "approvalId": "<approval-uuid>", "reviewNotes": "مطابقة كشف الحساب الرسمي." }
```

يتحقق الخادم من أن الموافقة تخص الإيداع نفسه ونوعها وإجراءها صحيحان، وأن مقدم الطلب ليس الموافق، وأن الموافق هو منفذ الاعتماد. ينفذ تحديث الإيداع وقيد الأستاذ المزدوج وتغذية المحفظة وإغلاق سجل الموافقة `EXECUTED` داخل معاملة قاعدة بيانات واحدة. أي فشل يعيد المعاملة بالكامل.

لا تعدّل جدول `wallets` مباشرة ولا تغيّر الرصيد من لوحة الإدارة. جميع الحركات من خلال `LedgerService` فقط وبـ DECIMAL لكل عملة مستقلة.

## 6. رفض الطلب والاستثناءات

ارفض عبر `POST /api/admin/deposits/{depositId}/reject` مع `rejectionReason` واضح وإبلاغ العميل. لا تحذف الطلب أو سجل المراجعة.

لا تعالج تلقائياً حالات المرجع المكرر أو استجابة مزود غير محسومة. استخدم `NeedsReconciliation`/`ManualReview` عند الشك، ثم أنشئ عنصر مطابقة وموافقة منفصلة.

## 7. المطابقة اليومية

- استورد كشف الحساب الأصلي من القناة/المحفظة في بيئة آمنة، ثم أرسل عناصر المطابقة إلى `POST /api/reconciliation/run`.
- راجع جميع حالات `DISCREPANCY`, `UNKNOWN_EXTERNAL`, `UNKNOWN_INTERNAL` ولا تسوّها بتغيير رصيد مباشر.
- أنشئ موافقة مالية لكل عنصر يحتاج معالجة، ثم أغلق المطابقة فقط باستخدام `POST /api/operational-approvals/{id}/closeout` مع مرجع دليل التنفيذ.
- لتعديل محاسبي، أنشئ أولاً قيد `ADJUSTMENT` مزدوجاً عبر مسار الأستاذ المعتمد ومرجعه `RECONCILIATION_ITEM`؛ closeout لا ينشئ قيداً ولا يغيّر رصيداً بنفسه.
- لا يقبل مسار closeout تصنيف فرق المبلغ على أنه مطابق ما لم يتساوَ المتوقع والفعلي بدقة.

## 8. الرقابة والتدقيق

- أرقام حسابات الاستقبال مقنّعة في سجلات التدقيق؛ لا تسجل بيانات الدخول أو OTP أو أسرار المحافظ.
- استخدم `GET /api/admin/deposits/channels/all` و`GET /api/admin/deposits/channels/legal-verification` لمراجعة الإعدادات وحالة التحقق.
- استخدم Kill Switch عند الاشتباه عبر `POST /api/admin/deposits/channels/{channel}/kill-switch` مع سبب موثق.
- جميع القنوات الخارجية تبقى MANUAL؛ أوضاع `DISABLED` و`BLOCKED_EXTERNAL` تمنع الظهور/الاستقبال.

## 9. ما يلزم قبل تفعيل قناة إنتاج

يلزم إكمال جميع حقول الحساب الحقيقية والتحقق من مستند ملكية الحساب والمستفيد، اعتماد شخص مستقل، فحص إظهار التعليمات للعميل، تجربة إيداع منخفض القيمة في الحساب الحقيقي بموافقة الأطراف، ثم مطابقة حركة البنك/المحفظة مع قيد الأستاذ. لم تُنفذ هذه الخطوات على حسابات حقيقية بواسطة هذا الفرع.
