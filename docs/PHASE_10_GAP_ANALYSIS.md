## 1. مرجعية المتطلبات والمعايير (Requirements Reference)

| الرمز | المرجع في خارطة الطريق | المتطلب الأساسي والضوابط |
| :--- | :--- | :--- |
| **AT-20** | Master Acceptance Tests | استعادة قاعدة البيانات من Backup: التحقق الآلي من سلامة القيود المالية وتطابق الدائن والمدين بنسبة 100% وتحقيق RTO < 30m و RPO < 5m. |
| **NFR-01** | Non-Functional Requirements | الأداء وزمن الاستجابة: < 300ms للعمليات العادية، وتحمل الضغط المتزامن (Concurrent Checkout) دون رصيد سالب أو ازدواجية. |
| **NFR-02** | Non-Functional Requirements | النسخ الاحتياطي والتعافي: أخذ لقطات مشفرة مع تجربة استعادة دورية مجربة وموثقة وتدقيق سلامة البيانات. |
| **NFR-06** | Non-Functional Requirements | صمود النظام واستمرارية الأعمال (Business Continuity): سلوك آمن عند انقطاع الكهرباء، أو سقوط البنك أو مزود الشحن أو شبكة SMS. |
| **NFR-08** | Non-Functional Requirements | قابلية الرصد والشفافية (Observability): قياس معدل الأخطاء HTTP 5xx/4xx، وزمن الاستجابة، وأقفال DB، وتأخر الطوابير، وأوامر المزودين المجهولة. |
| **AR-16** | Architecture Requirements | البنية التشغيلية: عزل Dev/Staging/Production، أسرار قوية مشفرة، مسار CI/CD مع فحص الهجرات وتراجع آمن (Rollback)، وتعمية بيانات الإنتاج عند النسخ. |
| **Checklist** | 09_PRODUCTION_LAUNCH_CHECKLIST | قائمة الإطلاق الإجباري الموقعة لاعتماد الجاهزية الفنية والمالية والتشغيلية. |

## 2. جدول تحليل الوضع القائم مقابل الفجوات (EXISTING / MISSING / CONFLICT / RISK)

| المجال التقني / التشغيلي | الوضع القائم (EXISTING) | الفجوة المحددة (MISSING) | التعارض المحتمل (CONFLICT) | المخاطر وسبل التخفيف (RISK & MITIGATION) |
| :--- | :--- | :--- | :--- | :--- |
| **1. عزل البيئات وتعمية البيانات (Env Isolation & Data Masking)** | يوجد ملف `.env` و `.env.example` مع فحص `validateProductionSecrets` لطول المفاتيح في `main.ts`. | غياب قوالب بيئة صريحة منفصلة لكل بيئة (`.env.staging.example`, `.env.production.example`)، وغياب سكربت تعمية/حجب بيانات الإنتاج الحساسة (PII Sanitization) عند استنساخ البيانات للاختبار. | لا يوجد تعارض مباشر مع الكود الحالي. | **مخاطر:** تسريب أرقام هواتف أو بيانات عملاء حقيقية لبيئة التطوير.<br>**التخفيف:** إنشاء سكربت تعمية تلقائي يحجب الهواتف والأسماء والأرصدة قبل تغذية Staging. |
| **2. الرصد المباشر ومقاييس النظام (Health & Telemetry Metrics - NFR-08)** | تطبيق NestJS يعمل مع معالجة الأخطاء والـ Logger القياسي. | غياب مسارات مخصصة لفحص الصحة الحية (`/api/health`) وتفاصيل الجاهزية (`/api/health/ready`)، ومقاييس الأداء التراكمية بصيغة Prometheus / JSON (`/api/monitoring/metrics`)، وعدم تتبع أقفال DB وتأخر الطوابير. | تعارض محتمل إذا كانت الفحوصات تستهلك استعلامات ثقيلة تؤثر على زمن الاستجابة. | **مخاطر:** تأخر اكتشاف العطل حتى يشتكي العملاء.<br>**التخفيف:** خدمة مراقبة خفيفة ومستمرة تخزن المقاييس في الذاكرة مع كشف فوري لأي شذوذ. |
| **3. إنذار المطابقة المالية اليومية ومسار التصعيد (Daily Finance Reconciliation Alert)** | تم بناء محرك التسوية الثلاثية في P05 وتقارير نهاية اليوم في P07. | غياب خدمة إنذار آلي ترسل تنبيهاً فورياً عند اكتشاف فروقات مالية أو أوامر مجهولة أو عدم توازن في الأستاذ العام، مع غياب مصفوفة تصعيد رسمية محددة بـ SLA. | يجب ألا تتجاوز التنبيهات صلاحيات الإدارة المالية. | **مخاطر:** تراكم فروقات مالية غير مكتشفة بين كشف البنك وأرصدة المزودين.<br>**التخفيف:** محرك إنذارات يصنف التنبيهات حسب الأولوية (`INFO`, `WARNING`, `CRITICAL`) مع تحديد مسؤول التدخل. |
| **4. النسخ الاحتياطي واختبار الاستعادة (AT-20 Backup & Restore Drill)** | وجود حاوية PostgreSQL في Docker Compose. | غياب سكربتات نسخ احتياطي آلية مع حساب البصمة الرقمية SHA-256، وغياب سيناريو اختبار آلي يثبت استعادة الـ Database وسلامة توازن دفتر الأستاذ العام بنسبة 100% وتحقيق RTO/RPO. | التأكد من عدم تعطيل المعاملات الجارية أثناء أخذ اللقطات. | **مخاطر:** نجاح عملية النسخ وفشل الاستعادة عند وقوع الكارثة.<br>**التخفيف:** كتابة اختبار AT-20 آلي وسكربتات تحقق تثبت سلامة القيود والبيانات قبل وبعد الاستعادة. |
| **5. اختبار الضغط المتزامن وصمود الطوابير (Stress Run & Worker Resilience)** | فحص الرصيد والـ Idempotency Key موجود في الخدمات الأساسية. | غياب اختبار إجهاد حقيقي (Stress Run) يحاكي 10 عمليات شراء متزامنة بنفس اللحظة برصيد محدود ويثبت منع الرصيد السالب تماماً، وغياب اختبار محاكاة انقطاع Worker أثناء المعالجة وتأكيد عدم تكرار الشحن. | احتمالية استهلاك موارد الـ CPU والـ Memory في بيئة الاختبار. | **مخاطر:** حدوث Race Condition ينتج عنه رصيد متاح سالب أو شحن مضاعف.<br>**التخفيف:** اختبارات Jest مكثفة تطلق وعود متزامنة (`Promise.all`) وتتحقق من قفل الصفوف والـ Idempotency. |
| **6. خطة أنابيب النشر الآمن والتراجع (CI/CD Pipeline & Safe Rollback - AR-16)** | وجود أوامر البناء والاختبار في `package.json`. | غياب ملف تدفق GitHub Actions يدمج فحص Linter، اختبارات الأمان، تجربة هجرة الـ DB (Migration dry-run)، وغياب سكربت وإجراءات موثقة للتراجع الآمن (Rollback) دون فقدان سجلات القيود المالية. | تعارض تراجع مخطط الـ DB مع البيانات المنشأة حديثاً. | **مخاطر:** نشر كود معطوب أو تعديل قاعدة بيانات غير قابل للتراجع.<br>**التخفيف:** سياسة تراجع تمنع حذف الجداول وتعتمد Non-destructive migrations مع سكربت فحص فوري. |
| **7. لوحة إدارة الجاهزية والعمليات (Web Admin Operations Dashboard)** | لوحة تحكم الإدارة تملك صفحات للمنتجات، والطلبات، والتقارير، والأمان. | غياب صفحة عمليات وتشغيل متكاملة (`/operations`) تعرض مؤشرات الأداء الحية، وتنبيهات النظام والمطابقة، وحالة النسخ الاحتياطي، ومحاكي أوضاع الطوارئ (Safe Mode). | تناسق التصميم مع بقية صفحات لوحة الإدارة. | **مخاطر:** تشتت مديري النظام بين أدوات خوادم متعددة دون واجهة مركزية موحدة.<br>**التخفيف:** بناء صفحة عصرية شاملة ترتبط مباشرة بـ APIs المراقبة والحالة التشغيلية. |

## 3. خطة العمل التنفيذية للمرحلة العاشرة (Phase 10 Execution Plan)

1. **المرحلة 1: طبقة البيانات والمشترك (`@digital-topup/shared` & `@digital-topup/database`):**
   - إضافة الـ Enums والـ Types الخاصة بالمراقبة، والصحة التشغيلية، وسجلات النسخ الاحتياطي، والإنذارات.
   - إضافة جدولي `system_alerts` و `backup_records` إلى `schema.prisma` مع توليد العميل وبنائه.
2. **المرحلة 2: وحدة المراقبة والصحة والإنذارات في الـ Backend (`apps/backend/src/modules/monitoring`):**
   - تطوير `HealthController` ومسارات `/api/health` و `/api/health/ready`.
   - تطوير `MonitoringService` و `MonitoringController` ومسارات المقاييس والإنذارات التلقائية.
   - تطوير محرك التحقق من المطابقة المالية `ReconciliationAlertEngine` ومصفوفة التصعيد.
3. **المرحلة 3: سكربتات النسخ الاحتياطي، التعمية، والتراجع (`scripts/`):**
   - تطوير `scripts/sanitize-staging-data.ts` لتعمية بيانات الإنتاج عند النسخ للاختبار.
   - تطوير `scripts/backup-db.ts` و `scripts/restore-db.ts` لحفظ واستعادة البيانات مع فحص SHA-256.
   - تطوير `scripts/rollback.ts` لتنفيذ التراجع الآمن وتفقد صحة النظام.
4. **المرحلة 4: تدفق الـ CI/CD والإعدادات التشغيلية:**
   - إنشاء `.github/workflows/ci-cd-pipeline.yml`.
   - إعداد ملفات البيئة `.env.staging.example` و `.env.production.example`.
   - إعداد تكوين Nginx و WAF مع معايير الأمان والتشفير وحماية الكوكيز.
5. **المرحلة 5: حزم الاختبارات المؤتمتة (AT-20، Stress Run، Worker Resilience، Provider Outage):**
   - اختبارات وحدة المراقبة والإنذارات والمقاييس (`monitoring.spec.ts`).
   - اختبارات الإجهاد المتزامن، استعادة النسخ الاحتياطي، صمود العمال، وتوقف البوابات (`concurrent-checkout-stress.spec.ts`).
6. **المرحلة 6: واجهة العمليات والجاهزية التشغيلية في لوحة الإدارة (`apps/web-admin/src/app/operations/page.tsx`):**
   - بطاقات الحالة اللحظية للخدمات (DB, Redis, Uptime, Latency).
   - جدول الإنذارات الحية ومسار التصعيد المالي.
   - لوحة سجلات النسخ الاحتياطي وRTO/RPO.
   - أدوات محاكاة الأعطال وزر التحول الآمن للطوارئ.
7. **المرحلة 7: التوثيق الشامل وبوابة الإغلاق:**
   - إعداد أدلة التشغيل، التعافي من الكوارث، تكاليف التشغيل والتراجع.
   - توقيع قائمة `09_PRODUCTION_LAUNCH_CHECKLIST.md`.
   - تقرير الإنجاز الشامل `docs/PHASE_10_IMPLEMENTATION_REPORT.md` وتحديث `docs/PROJECT_STATUS.md`.
