# مصفوفة معرفات العملاء وواجهات المحافظ اليمنية

> آخر مراجعة للمصادر العامة: 10 نوفمبر 2026. هذه المصفوفة تحدد ما هو معلن علناً وما يحتاج مستنداً أو موافقة مباشرة من المشغّل. ظهور كلمة API في موقع أو صورة لا يثبت وحده أن واجهة التاجر متاحة لحساب المنصة.

## 1. قواعد تسجيل معرف المرسل

كل عميل يحفظ معرف حساب التحويل مرة واحدة لكل محفظة، ويرتبط بالحساب والعميل والقناة. قيمة المعرف مشفرة في قاعدة البيانات ولا تظهر كاملة في القوائم.

| القناة | المعرف الذي يعرضه التطبيق | الوضع عند عدم وجود البديل |
|---|---|---|
| جيب JAIB | ALIAS وفق إعداد التشغيل المطلوب | يغيّر مسؤول القناة إلى PHONE إذا لم يظهر البديل في كشف استقبال التاجر |
| كاش CASH | يمكن استخدام ALIAS لأن الموقع الرسمي يذكر إمكانية إنشاء رقم بديل | PHONE هو رقم حساب Cash Pay المنشور في خطوات الدفع، ويجب التحقق من شكل مرسل التحويل في كشف التاجر |
| جوالي JAWALI | PHONE | رقم الجوال المرتبط بحساب المحفظة حسب شروط الخدمة |
| إيزي EASY | PHONE | الموقع الرسمي يذكر أن رقم الحساب هو رقم الهاتف |
| ون كاش ONE_CASH | PHONE افتراضياً حتى تأكيد المشغّل | يسمح مسؤول القناة بتغيير النوع بعد إفادة رسمية |
| أي محفظة أخرى | يحدد حسب مستند المشغّل ونموذج الحركة الواردة | PHONE أو WALLET_ID أو ACCOUNT_NUMBER بحسب ما يظهر فعلياً في كشف الاستقبال |

الأنواع المدعومة في الخادم: ALIAS وPHONE وWALLET_ID وACCOUNT_NUMBER. التغيير يتم من إعدادات القناة، ولا يجوز اختيار نوع لمجرد التخمين؛ يجب أن يطابق الحقل الذي يظهره حساب الاستقبال التجاري عند وصول تحويل العميل.

## 2. تصنيف مسارات التكامل

### كاش Cash Pay — واجهة تاجر رسمية معلنة

موقع Cash الرسمي يعلن Cash Pay للمتاجر والتطبيقات، ويذكر وجود فريق تقني يربط الخدمة عبر API، وأن المبلغ ينتقل من حساب العميل إلى حساب محفظة التاجر. كما يصف خطوات دفع تشمل رقم حساب العميل (رقم الهاتف المسجل) وكود الشراء الإلكتروني ورمز تحقق SMS.

هذا يعني أن Cash هي أول قناة في قائمة طلبات API المباشر. لكن الموقع لا ينشر في الصفحة العامة عناوين REST أو OpenAPI أو Sandbox أو نموذج توقيع webhook. لذلك لم يتم إنشاء endpoint تخميني ولم يتم تفعيل وضع API. المطلوب من Cash:
- عقد تاجر باسم المنشأة والنشاط المراد تحصيل مدفوعاته.
- دليل API الرسمي، Postman/OpenAPI، بيئة Sandbox، آلية التوقيع والاستعلام، رموز حالات الدفع والاسترداد.
- حساب Cash Pay تجاري وحساب استقبال باسم المنشأة، وإفادة مكتوبة عن الصلاحيات والحدود والرسوم والتسوية.
- بيانات اختبار أولاً، ثم بيانات إنتاج عبر مخزن أسرار؛ لا ترسل المفاتيح في Git أو المحادثة.

المصدر الرسمي: https://www.cash.com.ye/ar/خدمة-الدفع-الإلكتروني-كاش-باي-cash-pay
الاستفسار المنشور في الصفحة: customercare@tamkeen.com.ye / 8000333.

### إيزي EASY — قناة API معروضة لكن تفاصيل الربط غير منشورة

يعرض موقع Easy الرسمي قناة باسم API، ويذكر أن رقم حساب المشترك هو رقم هاتفه. لم أعثر في المصادر العامة التي راجعتها على مرجع REST أو Sandbox أو مستند اعتماد تاجر. الحالة إذن: طلب مستندات من المشغّل، وليس API جاهزاً للتشغيل.

الموقع: https://www.easy-fintech.com/
صفحة التواصل: https://www.easy-fintech.com/contact-us/

### جيب JAIB — لا يوجد مرجع API عام تم التحقق منه

يظل المسار اليدوي الحالي هو المتاح برمجياً إلى أن تقدم شركة عهد مستندات تاجر/API رسمية. معرف العميل الافتراضي في إعداد المنصة هو ALIAS بناءً على متطلب التشغيل، لكن يجب اختبار شكل المعرف الذي يظهر فعلياً في سجل حساب الاستقبال التجاري. إذا لم يظهر البديل، يحول إعداد القناة إلى PHONE ويعيد العميل حفظ معرفه.

لا يوجد اتصال شبكي إلى تطبيق جيب، ولا مسح لحساب العميل أو حساب التاجر من خادم المنصة دون واجهة رسمية أو موصل موثق.

موقع المشغّل: https://ahdfinancial.com/

### جوالي JAWALI — رقم الهاتف هو المعرف المنشور

شروط WeCash/جوالي تنص على أن الحساب يرتبط برقم الهاتف الذي يقر العميل بملكيته، وتصل إليه إشعارات العمليات. لم أجد مرجع API تاجر عاماً أو Sandbox منشوراً في المصادر التي راجعتها. لذلك يبقى PHONE هو نوع المعرف الافتراضي، وأي تكامل API يحتاج اتفاقية ودليلاً رسمياً من WeCash.

الشروط: https://jawali.com.ye/Terms_en/

### ون كاش ONE_CASH — API غير مثبت بمستند عام

لم أجد في المصادر الرسمية العامة التي راجعتها دليلاً للمطورين أو Sandbox لربط تاجر ون كاش. يبقى المسار اليدوي متاحاً بعد اعتماد القناة، ويظل PHONE افتراضياً حتى تأكيد نوع المعرف الظاهر في كشف التاجر.

## 3. موصل طرف ثالث اختياري: إيصالات Esaalat

تنشر منصة إيصالات مرجع REST API وWebhook للتجار. توضح الوثائق أن التاجر ينشئ Intent بمبلغ ومحفظة استقبال، ويربط مرجع التحويل الذي يدخله العميل، ثم تُطابق الخدمة المحفظة والمرجع والمبلغ وتبعث حدث payment.verified موقعاً. كما تتطلب محفظة استقبال على هاتف Android يعمل عليه تطبيق مراقبة، ورابط webhook عام.

المصادر الرسمية:
- مرجع API: https://esaalat.com/ar/api-reference
- الشروط: https://esaalat.com/en/terms
- الموقع: https://esaalat.com/ar

لكن Esaalat ليست API صادرة عن جيب أو جوالي أو ون كاش؛ شروطها تقول إنها ليست تابعة لمزودي المحافظ، وأن تطبيق Android يقرأ إشعارات SMS الخاصة بمحفظة التاجر ويرسلها إلى الخدمة. لذلك تصنفها المنصة كطرف ثالث منفصل، لا كواجهة معتمدة من مشغل المحفظة. موقعها يذكر أن الخطة المجانية تشمل محفظة واحدة وجهاز مراقبة واحداً و500 عملية موثقة شهرياً.

لم يتم ربط Esaalat أو إرسال بيانات العملاء إليها. قبل أي استخدام، يلزم:
1. موافقة مالك المنصة الصريحة على مشاركة بيانات معاملات الاستقبال مع طرف ثالث، مع مراجعة شروط الخصوصية والتعاقد والامتثال.
2. إنشاء حساب تاجر باسم المنشأة، وتسجيل محفظة استقبال مملوكة للمنشأة وجهاز Android مخصص وآمن.
3. تهيئة HTTPS webhook عام وحفظ client_secret وسر webhook في مخزن الأسرار.
4. تنفيذ اختبار Sandbox، والتحقق من HMAC على raw body والطابع الزمني، ومطابقة external_order_id مع طلب إيداع محلي، ومنع التكرار باستخدام intent_id/event_id.
5. رفض أحداث payment.unmatched أو payment.received التجريبية كإذن لإضافة رصيد إلى عميل؛ القيد يتطلب intent موثقاً مرتبطاً بالطلب وحالة VERIFIED ومبلغاً وعملة ومحفظة مطابقين.
6. الاحتفاظ بمراجعة مالية استثنائية عند اختلاف المبلغ أو المرجع أو المرسل أو تعذر المطابقة.

لا يجوز اعتماد رقم البديل أو الهاتف وحده كإثبات دفع. في مسار الطرف الثالث يجب أن يرتبط الحدث بطلب محدد ومحفظة الاستقبال الصحيحة والمبلغ والعملة والمرجع، وأن يتحقق توقيع webhook وتُعالج الإشعارات المتكررة بأمان.

## 4. سياسة القيد الآلي للوكلاء في المسار اليدوي

إذا لم يوجد موصل API رسمي/مصرح به، يراجع وكيل المحفظة سجل حساب الاستقبال التجاري الرسمي لا حساب العميل. وبعد التأكد من وصول التحويل يدخل:
- هوية المرسل كما ظهرت حرفياً (بديل/هاتف/معرف).
- مبلغ الحركة وعملتها.
- رقم الحركة الفعلي.
- آخر أربعة أرقام لحساب الاستقبال ومرجع سطر كشف الحساب.

لا تكفي صورة الإيصال التي رفعها العميل أو بيانات الطلب التي كتبها بنفسه. يقوم الخادم بالمطابقة مع المعرف المشفر المحفوظ ومرجع الحركة الفريد والمبلغ والعملة وحساب الاستقبال. عند نجاح الشروط وسياسة السماح الآمن فقط، ينفذ قيداً مزدوجاً تلقائياً دون موافقة مالية فردية؛ أما التناقض أو الحد اليومي أو فشل التحقق فيحول العملية إلى المالية.

سياسة القيد الآلي الجديدة:
- متوقفة افتراضياً.
- يجب تحديد كل قناة في allowlist صريحة.
- سقف مستقل للمبلغ لكل عملية ولكل عملة.
- سقف يومي لعدد عمليات كل وكيل وإجمالي القيمة لكل عملة.
- TOTP حديث من تطبيق المصادقة الخاص بالوكيل لكل عملية مؤهلة.
- رفض إعادة استخدام TOTP عبر Redis؛ غياب Redis يمنع القيد الآلي.
- عزل tenant، ومنع تكرار المرجع، وقيد دفتر أستاذ مزدوج، وسجل تدقيق.
- لا يسمح للوكيل بمراجعة مالية مستقلة لنفسه.

## 5. ملاحظات إطلاق

- وضع API لا يفتح بمجرد وجود كلمة API على الموقع. يجب أن يمر كل موصل بمستند رسمي، وسر إنتاج محفوظ، وSandbox، واختبارات توقيع وإعادة إرسال واستعلام وتسوية.
- لا ترسل مفاتيح API أو PIN أو OTP أو بيانات دخول المحافظ في المحادثة أو مستودع Git.
- جميع القنوات تظل محجوبة حتى اعتماد حساب الاستقبال والعقد والمتطلبات التنظيمية، واختبار Staging، والتوقيع على GO/NO-GO.
