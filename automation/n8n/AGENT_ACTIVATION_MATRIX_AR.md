# مصفوفة جاهزية وتشغيل وكلاء n8n الـ12

هذه المصفوفة تميز بين وجود Workflow في حزمة التصميم وبين السماح بتفعيله على المنصة. وجود ملف JSON لا يعني أن API أو مصدر البيانات أو صلاحية الخدمة جاهزة. جميع Workflows في الحزمة غير نشطة افتراضياً.

| # | الوكيل | الحالة المقترحة | ما يحتاجه قبل التفعيل | المحظورات الدائمة |
|---|---|---|---|---|
| 01 | مدير العمليات المركزي | مرشح للمرحلة الأولى بعد الإعداد | Webhook موثق، إعداد LLM من متغيرات n8n، اختبار تحليل/فشل النموذج | لا ينفذ تغييرات؛ لا موافقات مالية |
| 02 | مراقبة البنية التحتية | مرشح للمرحلة الأولى | GET /api/health و/api/health/ready؛ اختبار timeout وDEGRADED | لا Restart ولا تعديل DB/Redis |
| 03 | النسخ الاحتياطي والتعافي | مرشح مشروط باختبار محلي | نجاح نسخة مشفرة، ثم Restore drill على قاعدة اختبار محلية، ثم فحص Ledger | لا Production restore؛ BACKUP_CREATED لا يعني Restore |
| 04 | استقبال إشعارات المحافظ والإيداعات | محجوب عن التفعيل المالي | مصدر إشعار رسمي/موثوق، عقد تكامل معتمد، حذف PII، مطابقة مستقلة من مصدر الحساب الرسمي | لا اعتماد إيداع، لا رصيد، لا قبول صورة أو SMS وحده |
| 05 | محلل المطابقة والتسوية المالية | تحليل فقط؛ الربط الفعلي محجوب | Outbox موثوق من Backend أو كشف رسمي مصادق عليه وبيانات قراءة فقط | لا FORCE_MATCH، لا ADJUST_LEDGER، لا تغيير reconciliation status أو Ledger |
| 06 | الأرباح والتقارير المالية | محجوب حتى خدمة قراءة مخصصة | API read-only بهوية خدمة مستقلة؛ endpoints الحالية محمية JWT/Roles؛ فصل YER/USD/SAR | لا JWT مالك/مالية داخل n8n، لا سحب، لا قيود |
| 07 | مراقبة تنفيذ الشحن | تحليل حالات فقط | أحداث حالات موثوقة؛ endpoint استعلام مزود read-only ومفتاح idempotency | لا إعادة إرسال تلقائي عند UNKNOWN، لا Refund، لا تبديل مزود |
| 08 | دعم العملاء | مسودات بمراجعة بشرية | مصدر تذاكر معتمد، PII redaction قبل LLM، سياسة حفظ/إخفاء المحتوى | لا وعود استرداد/شحن، لا كشف الملاحظات الداخلية، لا تعديل تذكرة |
| 09 | كشف الاحتيال والأمن | توصيات وتصعيد فقط | أحداث Audit مختزلة، مصدر موثوق، قياس false positives ومراجعة بشرية | لا تجميد/فك تجميد محافظ، لا تعطيل قنوات، لا تجاوز RBAC/MFA |
| 10 | مراجعة ربط الحسابات | محجوب عن القرارات | تدفق مراجعة آمن ومختزل؛ صلاحية Owner تبقى في Backend؛ موافقة واضحة | لا قراءة identifiers كاملة، لا approve/reject، لا طلب كلمات مرور أو OTP |
| 11 | QA وDevOps | تحليل تقارير CI فقط | GitHub App/Token محدود القراءة وأحداث CI موثقة | لا Merge PR، لا نشر، لا Shell من payload، لا تغيير Secrets |
| 12 | موزع الإشعارات | مشروط بربط القناة | Telegram credential داخل n8n، Chat ID خاص، اختبار redaction وrate limit | لا PII ولا OTP ولا إثبات تحويل ولا تفاصيل مالية حساسة |

## نقاط التكامل المؤكدة والقيود

- Backend الحالي لا يملك Outbox عاماً أو Service Account/S2S token مستقلاً لـ n8n في النسخة التي تمت مراجعتها. لذلك لا يوجد ربط شامل تلقائي بأحداث المنصة حتى الآن.
- مسارا `/api/reports/dashboard-kpis` و`/api/reports/profit-and-performance` محميان بصلاحيات JWT/Roles. لا تستخدم حساب OWNER أو FINANCE داخل n8n لتجاوز هذا العائق. المطلوب هو هوية خدمة read-only مستقلة واختبار نطاقها.
- Workflows 04 و05 و06 و10 لا يجوز تحويلها إلى مسارات اعتماد مالي أو تعديل بيانات حتى لو أعاد LLM توصية عالية الثقة.
- Workflow 03 يستقبل أدلة التشغيل من سكربت محلي ولا يشغّل أوامر النظام من n8n.
- عقد LLM موصولة الآن بمسارات التنفيذ في الوكلاء 01 و04 و05 و06 و07 و08 و09 و10 و11. إعدادات النموذج من Runtime Settings ومتغيرات n8n الموثوقة، وليست من payload. مراقبة البنية التحتية حتمية.
- لا تنشر أي Workflow إلا بعد مراجعة Credentials، اختبار فشل الاعتمادية، وتأكيد أن كل عقدة كتابة غير مالية ومصرح بها صراحة. العمليات المالية تبقى داخل Backend بعد المصادقة والصلاحيات وسجل التدقيق والمعاملة الذرية.
