## الهدف والنطاق
جعل رحلة العميل قابلة للاستخدام بشكل موثوق على الهواتف وضمن اتصال ضعيف وخدمة دعم واضحة.

## الأعمال المطلوبة بالتسلسل
1. تحسين Web Customer لـMobile-first RTL وخطوات قصيرة للحجز/الشحن، مع استمرار إظهار تفاصيل الحساب المستفيد قبل التأكيد.
2. حفظ سجل طلبات وربط خدمات اختياريًا وإتاحة اختيار الحساب المخزن بأمان بعد موافقة العميل.
3. إشعارات حالة الإيداع/الطلب/الاسترجاع والتقرير الإداري فقط بعد وصول حدث مؤكد من Backend.
4. إنشاء مركز تذاكر دعم وربط كل تذكرة بـOrderID/DepositID/PayoutID دون عرض بيانات مالية لموظف غير مخوّل.
5. إتاحة عرض السبب وطلب استئناف ومراجعة بشرية للقرارات المؤثرة على العميل.
6. تحسين التجربة عند اتصال متقطع؛ يجب ألا يُرسل الزر نفس العملية مرتين بفضل idempotency.
7. تجهيز PWA اختياريًا؛ تطبيق Native Android/iOS قرار لاحق لا شرط للإطلاق طالما PWA يحقق الاحتياج.
8. تحديث سياسة Refund وتعليمات العميل عند فشل الشحن أو إدخال معرّف خاطئ قبل تنفيذ المزود.

## المخرجات التي يجب تسليمها
- واجهة Mobile UX محسنة
- مركز دعم وتذاكر
- In-app Notifications + اختيارية SMS/Email
- QA UX/accessibility/weak network

## اختبارات القبول الخاصة بالمرحلة
- [ ] اختبار Android low-end ومتصفحات سطح المكتب.
- [ ] مسار من التسجيل إلى إيداع إلى شراء إلى تذكرة دعم.
- [ ] إعادة الضغط بسبب شبكة ضعيفة لا ينشئ طلبًا ثانيًا.
- [ ] لا يسرب إشعار بيانات عميل آخر.

## أهم المخاطر والقيود
- انقطاع الإنترنت في اليمن
- إشعار نجاح قبل تأكيد المزود
- استخدام بيانات هوية زائدة في الواجهة

## بوابة الإغلاق (Definition of Done)
**اختبارات استخدام فعلية، وتجربة اتصال ضعيف، وتذاكر قابلة للرد.**

يجب إضافة سجل تنفيذ حقيقي يثبت: نتائج Unit/Integration/E2E، مخطط وتغييرات قاعدة البيانات، endpoints وواجهات UI، مراجع القيود المالية عند ارتباطها بالأموال، وتحديث Swagger والوثائق. أي تكامل لا يملك اعتمادًا رسميًا يوضع `BLOCKED_EXTERNAL` دون ادعاء إنجازه.
