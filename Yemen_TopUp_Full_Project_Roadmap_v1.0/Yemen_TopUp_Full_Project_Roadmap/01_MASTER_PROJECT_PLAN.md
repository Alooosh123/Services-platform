# MASTER PROJECT PLAN v1.0 — خطة المشروع من الصفر إلى التشغيل المستقر
**اسم المشروع:** Yemen Market Digital TopUp & Services Platform  
**نقطة البداية:** تطبيقان Web Customer وWeb Admin + API NestJS + Prisma + Strict Double-Entry Ledger.  
**هذا المستند:** مرجع الاستراتيجية والجدول المنطقي والانتقالات وليس تقرير إنجاز برمجي.

## 1) رؤية المنتج
منصة يمنية تتيح للعميل إنشاء حساب، تأكيد التحكم في هاتفه، شحن محفظته، اختيار تطبيق/خدمة وفئة، وإتمام شحن خدمات رقمية آليًا عندما يدعم المزود الربط الرسمي؛ وإلا فتنفيذ موثق يدويًا. يستطيع مدير المنصة إضافة التطبيقات والفئات، وضع هوامش خاصة بكل باقة، إدارة قنوات الدفع، مراجعة الأرباح والتسويات، وطلب سحب **الأرباح المحققة والقابلة للصرف فقط**.

## 2) المبادئ غير القابلة للتفاوض
1. مصدر الحقيقة المالي هو **Strict Double-Entry Ledger** وليس قيمة يمكن تعديلها من لوحة الإدارة.
2. استقلال محافظ YER وUSD وSAR؛ استخدام Decimal، منع تحويل أو جمع مبالغ عبر العملات دون عملية FX مستقلة.
3. الأسعار والتكاليف والعمولات وأسعار الصرف تُحفظ في Order Snapshot مع إصدار سياسة التسعير.
4. كل إرسال إلى مزود شحن أو دفع: Idempotency، مرجع خارجي، Outbox/Queue، سجل أحداث، سياسة Unknown Outcome.
5. لا تُحجز أرباح المالك القابلة للسحب قبل تحقق الإيراد/التسوية والتحقق من النقد المتاح والاحتياطيات.
6. الربط بالخدمات الخارجية مرهون بالتوثيق الرسمي والموافقات؛ ممنوع محاكاة التكامل وإعلانه إنتاجيًا.
7. واجهات عربية RTL متجاوبة، والصلاحيات تُطبق في Backend لا واجهة العرض وحدها.
8. تقرير حالة صادق يميز **Reported / Verified / Blocked / Not Started**.

## 3) مخرجات النظام النهائية
- متجر ويب للعميل ومركز حسابات وخدمات مرتبط بإذن العميل، تدفقات شحن ورصيد وطلبات.
- لوحة إدارة مستقلة لإدارة الفئات والمنتجات والأسعار والأرباح والمحافظ والحسابات والطلبات.
- طبقة دفع وإيداع وتسوية مع قنوات محلية قابلة للتفعيل/الإيقاف.
- منظومة Provider Adapters للشحن، متابعة حالة التنفيذ، منع التكرار، والتعامل مع الإخفاقات.
- وكيل AI مساعد لتهيئة الطلبات والتحقق من قواعدها ورصد المخاطر مع ضوابط بشرية وامتثال.
- حسابات مالية: محافظ العملاء، أرصدة المزودين، النقد، التزامات المحفظة، المبيعات/التكلفة، أرباح مالك المنصة.
- تقارير يومية دورية وأرشيف التسويات وحالات السحب والأرباح المقدّرة والمحققة.
- مراقبة ونسخ احتياطية واختبارات واستجابة للحوادث وإطلاق تجريبي ثم عام.

## 5) بوابات القرار المرحلية (Go/No-Go)
- **Gate A — تصميم العمل:** اعتماد مالك المشروع نطاق النسخة الأولى، المتطلبات السبعة، وآلية التمويل وحسابات التجار.
- **Gate B — المحاسبة:** نجاح اختبارات التوازن والاستقلال والخصومات المتزامنة ومنع المعاملات المكررة.
- **Gate C — مزودو الخدمة:** وجود شريك واحد على الأقل يدعم التنفيذ الفعلي أو نموذج يدوي مضبوط ومصرّح به.
- **Gate D — المدفوعات:** تحقق ملكية حسابات الاستقبال، شروط مزود الدفع، التسوية والعمولات وقابلية سحب الأرباح.
- **Gate E — الحماية:** مراجعة الالتزامات المالية/التنظيمية ذات الصلة ومخاطر OTP/SIM swap وAI.
- **Gate F — إطلاق:** بيئة Staging، مراقبة، backups واختبار الاستعادة، سجل حوادث، تدريب الفريق، قبول UAT.

## 6) الأدوار المقترحة
- **مالك المنتج:** اعتماد سياسة الربح، المنتج، القنوات، فترة احتجاز الأرباح، والقرارات التجارية.
- **Technical Lead:** قواعد التصميم، مراجعات الكود، التكامل بين الوحدات، الأدوات، API.
- **Financial Controller:** الدليل المحاسبي، قيود الأموال، إقفال اليوم، التسويات، المصادقات.
- **Integration Engineer:** الشركاء، OAuth/API, webhooks, retries, sandbox.
- **Security/Compliance:** المصادقة، صلاحيات السحب، متطلبات الهوية والموافقات وأدلة التدقيق.
- **QA:** سيناريوهات وحدات/تكامل/E2E وتحقيق شروط القبول.
- **Operations/Support:** معالجة الاستثناءات والطلبات المجهولة والتقارير اليومية.

## 7) تقدير ترتيبي غير ملزم
في حال فريق صغير ومزود خدمات واحد وقناة مالية تدعم الاختبار:
- P00/P01/P02 Audit: 1–2 أسبوع.
- P03–P04: 3–6 أسابيع.
- P05–P07: 4–8 أسابيع **بشرط توافر وثائق وبيانات اعتماد الجهات الخارجية**.
- P08–P10: 3–6 أسابيع مع عمل متوازٍ على الاختبار والأمن.
- P11–P12: 2–4 أسابيع للتجربة والمراقبة والتسليم.
هذه نطاقات تخطيطية لا وعود زمنية؛ التكاملات الخارجية والموافقات والامتثال قد تغيّر الجدول جذريًا. تحديث التقدير بعد Audit للكود وموارد الفريق.

## 8) خطة الإطلاق على دفعات
- **MVP 1:** إدخال يدوي موثق من شركة الشحن + الدفع من المحفظة + لوحة الإدارة + تسويات يومية.
- **MVP 2:** شحن آلي لمزود واحد مع Sandbox موثق؛ إيداع آلي لقناة معتمدة إن توفرت.
- **Release 1.0:** تحكم ديناميكي كامل بالتسعير، سجل الأرباح، سحب المالك وفق السياسة، Agent Assist، دعم المستخدمين.
- **Release 1.1+:** مزودون متعددون، تحسين توصية القنوات، تطبيق جوال أصلي حسب الحاجة.

## 9) معيار اكتمال المشروع
ينتهي **التنفيذ والإطلاق** عند وجود تشغيل قابل للمراقبة والتعافي، تحقق مالي من طرف إلى طرف، طلبات حقيقية موثقة، سياسات ربح وسحب صحيحة، أمن وامتثال، دعم عملاء، وخطة استمرارية. أما **الصيانة** فلا تنتهي؛ تُنقل إلى التشغيل المنظم P12.

## 10) نقاط عدم يقين حاسمة
- هل المنصة تاجر شحن رقمي فقط أم تريد إصدار أو إدارة أرصدة نقود إلكترونية نيابة عن عملاء؟ ذلك يغيّر الالتزامات والعقود.
- ما هو مزود الشحن الفعلي وماذا يدعم معرف اللاعب/رقم الهاتف؟
- أي بنك/محفظة توفر API تجاريًا وسحبًا/تحويلًا آليًا؟
- هل تريد المالك من مال المنصة توزيع أرباح قابلة للسحب، أم مجرد رؤية رصيد محاسبي للأرباح؟
